# 批量入库模板

本目录提供批量入库用的两张表：

| 文件 | 用途 | 是否必需 |
| --- | --- | --- |
| [样本登记表.csv](样本登记表.csv) | 一行登记一份样本 | 必需 |
| [分项得分.csv](分项得分.csv) | 样本的分项技术得分 | 可选 |

两张表都是 UTF-8（带 BOM）的 CSV，Excel 可直接打开；保存时选“CSV UTF-8（逗号分隔）”。模板中的两行是虚构示例，正式填写前删除。编号、目录与文件命名遵守[案例与数据规范](https://github.com/zys743551828-art/tender-docs/blob/main/03-数据与案例/数据管理规范.md) §2.4，由程序自动完成，登记人不需要手工改名或建目录。

## 1. 一行是什么

一行 = 某项目／标段下某企业的**一次实际提交**：该项目的招标文件（含全部补遗）+ 该企业实际提交的技术标正文 + 这份正文得到的官方技术分。

- 同一项目有几家企业的正文，就登记几行；各行的招标编号、标段、招标文件填法一致，程序按“招标编号＋标段”归为同一项目，可做同场排名。
- 同一企业在同一项目只登记实际提交的那一版正文；修改稿、未提交稿不登记。
- 本公司历年投标（每个项目只有本公司一份）照常一行一份。

## 2. 样本登记表各列

列名和顺序固定，不要增删、改名或调换；末尾的“同场技术分”“入围分数线”两列可整列省略。

| 列 | 必填 | 填法 |
| --- | --- | --- |
| 样本编号 | 否 | 一般留空，程序接着库里最大编号分配 CASE-xxx；入库报告列出分配结果，可回填 |
| 项目名称 | 是 | 招标公告上的全称 |
| 招标编号 | 是 | 同一项目各行必须一致；纯数字编号在 Excel 里先把该列设为“文本”，防止变成科学计数 |
| 标段 | 否 | 如“一标段”；不分标段留空 |
| 地区 | 是 | 省＋市（＋县区），如“安徽省合肥市” |
| 工程类型 | 是 | 市政道路／排水管网／综合市政／园林／房建／其他 之一；“其他”的具体类型写进备注 |
| 评分办法 | 是 | 综合评估法／经评审的最低投标价法／技术入围后价格竞争；其他办法照招标文件原文名称填写 |
| 投标企业 | 是 | 营业执照全称 |
| 本公司 | 是 | 是／否 |
| 提交日期 | 是 | 投标截止日，YYYY-MM-DD（Excel 改写成 2026/4/20 也能识别） |
| 招标文件 | 是 | 文件名；招标文件与补遗、答疑、澄清多份时用英文或中文分号隔开，**按发布顺序**；第一份为招标文件，之后文件名含“补遗／答疑／澄清／补充／修改／变更”的记为补遗，其余记为招标文件分册 |
| 技术标正文 | 是 | 一个文件名，须为 PDF |
| 技术分 | 是 | 官方技术总分；未公布写 `/`（保留未知，不记为零）；留空按未公布处理并在报告中提示 |
| 技术满分 | 是 | 招标文件规定的技术部分满分，正数 |
| 成绩口径 | 是 | 技术总分／综合总分。只拿到综合总分时选“综合总分”，此时“技术分”列填综合总分；该样本可用于跑预测，不作技术标签 |
| 聚合方式 | 否 | 评委平均／去最高最低平均，或公示原文写法 |
| 成绩来源文件 | 否 | 官方评分表或评标结果公示原件的文件名 |
| 成绩来源页码 | 否 | 成绩所在的 PDF 物理页（从 1 数起，不是印刷页码） |
| 成绩来源类型 | 是 | 官方原件／公司台账／口头报送 |
| 结果 | 否 | 入围／未入围／被否决／中标／未中标／未知 |
| 成绩取得日期 | 否 | 拿到成绩的日期，YYYY-MM-DD；留空表示晚于提交日期但具体日期未登记 |
| 备注 | 否 | 其他说明 |
| 同场技术分 | 否 | 同一项目／标段**所有投标人**的官方技术分，分号隔开，未公布的写 `/`，如 `52.3;48;/`；同一项目只需在一行填写，多行填写时必须一致（顺序不限） |
| 入围分数线 | 否 | 技术入围的分数线（技术分口径）；同一项目多行填写时必须一致 |

成绩只有在“成绩来源类型”为官方原件、且填了成绩来源文件和页码时记为已核验（verified），其余记为待核验（pending）。

## 3. 分项得分表（可选）

放在登记表同一目录、文件名为 `分项得分.csv` 时自动读取，也可用 `--items` 指定。一行一个评分项：

| 列 | 填法 |
| --- | --- |
| 样本编号或登记表行号 | 填样本编号（CASE-xxx），或该样本在登记表中的 Excel 行号（表头为第 1 行，第一条数据为第 2 行） |
| 评分项 | 招标文件评分项原文或简称 |
| 得分 | 该项得分；未公布写 `/` |
| 满分 | 该项满分 |
| 评委 | 有评委逐人分时填评委标识（如“评委1”），此行为单个评委的分；留空表示该项最终得分 |

最终得分各项合计与技术分相差超过技术满分的 5% 时，报告提示核对（不拒收）。分项只随新入库的样本写入；已入库样本的资料清单不改写。

## 4. 原件与文件名

把原件放进一个收件目录，平铺或分子目录均可。程序按文件名在收件目录中递归查找：

- 不区分大小写，忽略空格，全角与半角字符视为相同；登记时可以省略扩展名。
- 同名文件出现在多个子目录且内容不同，判为“文件名歧义”并拒收该行；此时在登记表中写相对收件目录的路径（如 `张三提交/技术标.pdf`）即可区分。内容完全相同的重名文件不算歧义。
- 同一份招标文件被几家企业共用时，各行写同一个文件名，不必复制多份。

原件只复制、不改动。归档后的文件名由程序统一生成（如 `CASE-012_技术标_示例甲市政_20260420.pdf`），原文件名保存在资料清单的 `original_filename`。

## 5. 原件存放位置

原件（PDF 等）不进入 git，本仓库的 `.gitignore` 排除了常见原件类型。三处位置各司其职：

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| 本仓库 | 资料清单.json、README、评分配对集.json、入库报告.md | 每个文件记录 SHA-256、字节数、页数与存储键 `storage.key` |
| 对象存储（阿里云 OSS，S3 兼容） | 原件 | 按内容寻址：`originals/sha256/<前两位>/<sha256><扩展名>`；同一键只写一次，已有不同对象时拒绝覆盖；对象元数据 `x-amz-meta-sha256` 记录校验值 |
| 本地缓存 | 原件，按 `CASE-xxx_地区_工程简称/01-招标资料/…` 排列 | 环境变量 `TENDER_DATASETS_CACHE`，默认 `~/.cache/tender-datasets`；评分配对集中的路径相对缓存根 |

桶名、端点和密钥属于部署配置，不写入清单。在 tender-research 环境中安装存储依赖并设置环境变量：

```bash
pip install -e ".[store]"
export TENDER_STORE_ENDPOINT=https://oss-cn-hangzhou.aliyuncs.com   # 按桶所在地域
export TENDER_STORE_REGION=cn-hangzhou
export TENDER_STORE_BUCKET=<桶名>
export TENDER_STORE_ACCESS_KEY_ID_FILE=~/.config/tender/oss_key_id          # 也可直接设置 TENDER_STORE_ACCESS_KEY_ID
export TENDER_STORE_SECRET_ACCESS_KEY_FILE=~/.config/tender/oss_key_secret  # 文件权限设为 600
```

OSS 端点默认使用虚拟主机寻址，写入时附带 `x-oss-forbid-overwrite`；其他 S3 兼容服务使用 `If-None-Match: *`。两者都在上传前先查询该键，上传后再核对字节数与校验值。

## 6. 运行

在 tender-research 仓库环境中执行：

```bash
# 先试运行：只校验并打印报告，不写任何文件
python -m tender_research.intake --sheet 样本登记表.csv --inbox 收件目录 --datasets ../tender-datasets --dry-run
# 确认无误后正式入库，并把新原件上传到对象存储
python -m tender_research.intake --sheet 样本登记表.csv --inbox 收件目录 --datasets ../tender-datasets --upload
```

`--datasets` 省略时取环境变量 `TENDER_DATASETS`，再省略取与 tender-research 同级的 tender-datasets；`--cache` 省略时取 `TENDER_DATASETS_CACHE`。建议先登记 10 份试点，报告无拒收后再登记全量。

- 带 `--upload` 而对象存储未配置时，程序在写入任何文件之前报错并列出缺少的环境变量。
- 不带 `--upload` 时原件只进入本地缓存，报告的“对象存储”一节列出待上传的文件；之后运行 `python -m tender_research.store push` 补传。
- 入库后提交本仓库中本次生成的案例目录（只有资料清单与 README）、评分配对集.json 与入库报告.md。

重复运行是安全的：已入库的样本（同样本编号且同正文校验值，或编号留空时同项目、同企业、同正文校验值）跳过，已有案例目录从不覆盖；缓存中已有相同文件时保留，已有不同文件时报错。被拒收的行改正后再次运行即可补入，不影响已入库样本。

## 7. 存储命令

```bash
python -m tender_research.store status                       # 清单登记的原件数，缓存、仓库工作区与桶中各有多少
python -m tender_research.store push                         # 上传清单登记、本地有而桶中没有的原件
python -m tender_research.store verify                       # 逐个核对桶中对象存在且字节数、校验值一致
python -m tender_research.store fetch                        # 把缺少的原件下载到缓存并核对校验值
python -m tender_research.store fetch --case CASE-012        # 只取一个案例
python -m tender_research.store fetch --pairs ../tender-datasets/评分配对集.json   # 只取配对集样本的招标文件与正文
```

`push` 的来源依次为本地缓存和本仓库工作区；桶中已有相同对象跳过，已有不同对象报错且不覆盖。`fetch` 下载后核对 SHA-256，不符时不留下文件。各命令输出 JSON 汇总，有缺失、不符或失败时退出码为 1，未配置时为 2。

仓库中已被跟踪的原件（CASE-001、公开规则资料）同样由 `push` 上传。`push` 与 `verify` 均通过（`verify` 的 missing 与 mismatch 为 0）后，可把它们移出版本管理，工作区中的文件保留：

```bash
python -m tender_research.store push
python -m tender_research.store verify
cd ../tender-datasets
git rm -r --cached -- '*.pdf'
git commit -m "原件移至对象存储，仓库保留清单与校验值"
```

新克隆的仓库没有原件。需要原件的程序读取缓存时运行 `store fetch`；仍按本仓库目录读取原件的程序，用 `python -m tender_research.store fetch --dest ../tender-datasets` 把原件恢复到工作区（这些文件被 `.gitignore` 排除，不会再次提交）。

## 8. 输出与报告

正式入库写入：

- 本仓库：每个样本一个 `CASE-xxx_地区_工程简称/` 目录，含 README.md 与资料清单.json（1.3 版，成绩在 `assessment.official_results`，每个文件带 `storage.key`，正文另带 MinHash 签名）。
- 本地缓存：同名案例目录下的 01-招标资料、02-投标文件，有成绩来源文件时另有 03-评审结果。
- 本仓库根目录的 `评分配对集.json`：库中全部 1.3 版样本的配对清单，供系统批量预测和评测使用。`datasets_root` 为缓存根，文件路径相对缓存根，`storage_key` 为对象存储键；`eligible` 为是的样本进入监督评测，否则 `exclusion` 说明原因。
- 本仓库根目录的 `入库报告.md`：本次结果。

报告各部分的含义：

| 部分 | 含义 |
| --- | --- |
| 汇总 | 登记行数；通过 = 本次入库 + 已入库跳过；拒收行未入库、不占编号 |
| 本次入库 | 每行分配的样本编号、目录、技术分、模板组及是否进入监督集 |
| 已入库（跳过） | 已在库中的行及其编号，编号留空的行可据此回填 |
| 对象存储 | 上传结果，或只在本地缓存、待上传的文件及存储键 |
| 问题清单 | 按类别列出，每条有登记表行号与处理建议；标“拒收”的类别必须改正后重跑，其余为提示 |

不进入监督集的原因：

| exclusion | 含义 |
| --- | --- |
| missing_label | 技术分未公布 |
| composite_not_technical | 只有综合总分 |
| no_text_layer | 正文平均每页不足 50 字，多为扫描件，需 OCR |
| duplicate_body | 正文与库中较早的样本完全相同，不形成独立样本 |
| score_out_of_range | 技术分小于 0 或超过技术满分 |
| missing_files | 缓存中的原件大小与清单不符（缓存中缺少原件不影响资格，报告提示用 `store fetch` 取回） |

模板组（template_group）：正文高度相似（字符 5-gram 的 MinHash 估计 Jaccard ≥ 0.5）、同一项目或正文相同的样本归入同一组，评测时同组样本不拆到训练与测试两侧。签名在入库时写入资料清单，没有缓存原件也能分组。组号按当次配对集生成，库中样本增加后可能重新编排。
